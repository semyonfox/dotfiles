# Personal Infrastructure Operations

Use this class-level skill when Semyon asks to inspect, recover, run, deploy, or troubleshoot his personal infrastructure: homelab/server Docker stacks, NAS/media storage, cloud accounts and bills, workstation/devops CLI setup, backed-up credentials, Jenkins deployments, Tailscale/SSH access, Pi-hole/LAN DNS, or related local-device admin incidents.

The goal is practical operations with guardrails: discover the real state first, preserve secrets and data, make scoped changes only when requested or safe, and verify with live commands before reporting success.

## Operating principles

1. **Inventory before mutation.** Confirm host, path, process owner, config source, credentials, and live service state before changing files or restarting anything.
2. **Secrets stay secret.** Never paste access keys, tokens, refresh tokens, raw credential files, or provider secrets into chat. Redact values and report profile names, account suffixes, service names, regions, and non-secret config only.
3. **Backups are first-class evidence.** Semyon's NAS/device dumps under `/mnt/media/users/semyon/` often contain config and credential directories. Search them before asking for login roulette.
4. **Separate apparent success from live health.** A green Jenkins job, restored token file, or running container is not enough; verify with container logs, API/status probes, account identity checks, or CLI auth status as appropriate.
5. **Default to read-only for storage and network audits.** Deletions, firewall/router/DNS changes, account changes, and billing-impacting actions require explicit approval unless the user's request already approves a precise destructive scope.
6. **Write durable artifacts when setup/recovery is broad.** Save inventories, raw logs, manifests, or benchmark outputs to files and summarize the important result in chat.

## Homelab Docker stacks and server-stacks convention

Use this when creating, moving, editing, documenting, deploying, or verifying Docker Compose/Portainer stacks on Semyon's server.

Canonical layout:

```text
/home/semyon/server-stacks/<stack>/
├── README.md
├── stack.yaml
└── stack.env        # only when needed

/home/semyon/server-stacks/data/<stack>/   # runtime/generated app data
```

Workflow:

1. Inspect nearby stacks plus `/home/semyon/server-stacks/README.md` and `docs/reference/RUNTIME_DATA.md` before writing.
2. Keep app/runtime data under `server-stacks/data/<stack>/`; do not leave new services in ad-hoc `/home/semyon/<service>/` directories unless explicitly requested.
3. If there is both an app repo and a `server-stacks` deployment repo, inspect and commit each deliberately. Stage exact files only; do not sweep unrelated `.env`, backup, or generated files into commits.
4. Validate Compose with `docker compose -f stack.yaml config`; deploy only when requested; verify with `docker ps`, logs, healthchecks, and local/public HTTP probes.
5. For Jenkins-managed deployments, query Jenkins, scan the build console, wait for its terminal `Finished: SUCCESS` marker after pushes, then re-check live containers and probes. A job can emit intermediate successful test results before a later build/deploy failure. For Git LFS checkout failures, database smoke-test network diagnosis, and Compose container-name conflicts, follow `references/jenkins-git-lfs-and-compose-deploy-repair.md`.
6. For public-email alias migrations, configure inbound routing before exposing the alias, update both public source and runtime support-email settings, and verify served content plus the service health after a scoped redeploy. Never edit a secret-bearing env file with a diff-producing tool that could expose neighbouring values; make an exact key replacement and report only the non-secret setting. See `references/public-email-alias-routing-and-app-deploy.md`.

## Cloud/provider account recovery and billing triage

Use this for AWS/GCP/Azure-style account discovery, credential recovery, tiny recurring charges, and account-cost attribution.

1. Search local and NAS backup roots for provider config directories before asking Semyon to sign into dashboards. For AWS, look for `.aws`, accidental `.asw`, `credentials`, and `config` files while pruning noisy caches.
2. Summarize recovered config without leaking secrets: profile names, regions, account IDs/suffixes, and auth status only.
3. Before copying recovered credentials into active config directories, back up existing directories with a timestamped suffix, create restrictive destination permissions, and avoid filesystem features unsupported by the target.
4. Verify with non-destructive reads first: STS identity, billing/cost APIs, list/remotes, or provider-specific whoami/status commands.
5. Explain bills by account, service, usage type, and region. Tiny bills are often CloudWatch alarms, DNS/hosted zones, object storage requests, tax, or residual managed-service/API usage rather than compute.

## OSINT API account setup for SpiderFoot

Use this when Semyon asks to add free/free-tier OSINT APIs to SpiderFoot or similar recon tooling. Treat this as credential-bearing infrastructure work, not casual browsing:

1. Unlock and verify Bitwarden/Vaultwarden first; do not generate account passwords or retrieve API keys unless they can be saved immediately.
2. Create a dedicated vault folder and one item per provider, including signup URL, username, generated password, SpiderFoot setting name, and a hidden/custom API-key field.
3. Expect provider signups to require email verification, CAPTCHA, or anti-bot checks. If headless browser automation stalls, save a `pending signup` vault item and hand the manual verification step to Semyon rather than fighting the CAPTCHA or leaving credentials in temp files.
4. Configure SpiderFoot via serialized colon-form keys (`sfp_alienvault:api_key`, `sfp_abstractapi:phonevalidation_api_key`), then verify `/optsraw` only as `SET`/`empty` without printing secrets.
5. Delete temporary `BW_SESSION`, generated password files, and exported vault JSON/base64 payloads at the end of the run.

## DevOps CLI workstation setup and config recovery

Use this when a server/workstation needs to be ready for platform work or when CLI configs must be restored from backups.

Standard CLI surface to inventory/install as relevant:

- Cloud/core: `aws`, `gcloud`, `gsutil`, `bq`, `wrangler`, `cloudflared`, `gh`
- Infra/containers: `docker`, `docker compose`, `kubectl`, `helm`, `terraform`, `pulumi`
- Platform CLIs: `flyctl`, `doctl`, `supabase`, `firebase`, `vercel`, `netlify`, `railway`, `neonctl`, `sentry-cli`, `stripe`
- Secrets/storage/utilities: `op`, `doppler`, `rclone`, `s5cmd`, `jq`, `yq`

Workflow:

1. Check OS/architecture, PATH, `~/.local/bin`, Node/npm/bun, and existing versions first.
2. Install user-local where possible; symlink npm global binaries into `~/.local/bin` if the active PATH misses an nvm prefix. If `NPM_CONFIG_PREFIX=$HOME/.local` but `node`/`npm` are nvm-owned and symlinked from `~/.local/bin`, do not run `npm install -g npm@latest` into `~/.local` — it can fail with `EEXIST` on `~/.local/bin/npm`; instead run the npm sweep with `env -u NPM_CONFIG_PREFIX npm install -g ...` against the active nvm prefix, then refresh the `~/.local/bin` symlinks.
3. For globally installed Node CLIs which depend on `postinstall` payloads (for example native Claude Code/OpenCode launchers), do not hard-code paths inside `node_modules` or permanently enable all scripts. After the normal install, use `npm rebuild -g --foreground-scripts <package>` and, on npm builds enforcing `allow-scripts`, scope the permit to the known package for that invocation: `NPM_CONFIG_IGNORE_SCRIPTS=false NPM_CONFIG_OMIT= NPM_CONFIG_ALLOW_SCRIPTS='<trusted-package-list>' npm rebuild -g --foreground-scripts <package>`. Verify with each CLI's `--version`. A rebuild can misleadingly report success while hooks are blocked, so require evidence that the named `postinstall` hooks actually ran or that the CLI now starts.
4. Restore only expected config directories from trusted backups, backing up current config first: `~/.aws`, `~/.wrangler`, `~/.cloudflared`, `~/.docker`, `~/.config/gh`, `~/.config/rclone`, `~/.config/configstore`, `~/.config/gcloud`, `~/.kube`, `~/.terraform.d`.
5. For broad credential cleanup/consolidation from NAS/device dumps, use the manifest pattern in `references/dev-cli-credential-consolidation.md`: targeted inventory, redacted metadata only, timestamped local backup bundle, copy to canonical homes with `0600`/`0700`, verify SHA256, then delete only exact migrated NAS source files. Re-run the targeted inventory afterward to catch older snapshot duplicates.
6. Run version checks plus safe auth probes (`aws sts get-caller-identity`, `gh auth status`, `rclone listremotes`, `wrangler whoami`, `gcloud auth list`, etc.) with redaction, only when the relevant binaries are installed.
7. **Keep one owner per CLI.** Before adding a CLI to a shell `update()` function, resolve the interactive-shell binary (`command -v`, `readlink -f`) and package owner (`pacman -Qo`/equivalent). Do not also globally install an OS-package-managed CLI with npm/pnpm: a user-local shim can shadow the working distro binary and its blocked postinstall/native optional dependency. For a stale npm shim, remove it only after confirming it is a symlink into the expected npm global root; then make the updater verify the package-manager-owned binary/version rather than reinstalling it. Keep npm only for CLIs intentionally managed there (for example a user-local Codex install).

For a Linux x86_64 Tauri/AppImage release, query the upstream GitHub release/latest manifest, download the specific `linux-x86_64` asset to a temporary sibling, mark it executable, then atomically publish it under `~/.local/opt/<app>/<App>.AppImage`. ## NAS, disk, Btrfs, and media storage operations

- For a server that is a single point of failure for code, Git history, AI training/recovery state, and homelab configuration, build permission-restricted timestamped NAS snapshots with `rsync --link-dest`, a `COMPLETE` marker, manifest, recovery inventory, mount guard, bounded retention, and a persistent systemd timer. Preserve AI SQLite/JSONL state and database sidecars; quiesce or use SQLite backup APIs for critical live databases, then verify representative hashes and database integrity before reporting success. For long oneshot copies, monitor systemd `SubState=start` rather than relying on `is-active --quiet`, which may be non-zero while still activating. See `references/server-ai-code-nas-backup.md`.
- For local disk pressure, start with read-only `df`, top-level `du -x`, and concise `docker system df`; preserve AI logs/sessions such as `.t3-code`, `.hermes`, `.claude`, and `.codex` unless Semyon explicitly says otherwise. Compare `df` with `du -x`: a material gap commonly comes from root-owned Docker overlay/image data, deleted-but-open files, or ext4 reserved blocks. Check `docker system df` for images/containers/volumes/build-cache reclaimability and inspect deleted-open handles with `lsof +L1` (or a `/proc/<pid>/fd` read-only scan if privileged `lsof` is unavailable) before claiming the space is unaccounted for. Treat staging/recovery directories and agent state as review-only, not cache, until Semyon approves an exact scope.
- For SSD/NAS cache questions, distinguish a server-local working tier from a transparent NAS cache. First measure server↔NAS network with bidirectional `iperf3`, NAS-local direct sequential I/O, server-NFS direct I/O, and latency/loss; remove every temporary test file. When the server’s network path is slower than NAS disks, use its SSD only for bounded, regeneratable high-churn paths (transcodes, incomplete downloads, unpack/repair/import staging, thumbnails, build/app caches). Keep originals/completed media on NAS. A direct client→NAS transfer never benefits from a server SSD; routing it through a Wi-Fi server adds a hop. Do not present RAM or a laptop battery as durable storage: Linux page cache is opportunistic and clean shutdown can flush writes, but abrupt failure can still lose dirty data. Avoid a broad NAS SSD write-back cache unless its recovery semantics, power protection, and actual NAS-local workload justify it.
- For recovered AI-agent archive/staging cleanup (`ai-yoink-*`, `ai-staging`, copied `.claude`/`.codex`/`.t3`/T3Code state), dedupe by recursive content hashes, compare live system AI dirs read-only, delete/move only inside approved staging roots, write manifests, and flatten into one clean location rather than leaving surprise `consolidated-*` nesting. If Semyon says active worktrees are still in progress, report their size but do not touch them. See `references/local-ai-staging-dedupe-consolidation.md`. Do not touch project worktrees during disk cleanup unless Semyon explicitly asks; he may be actively working across them and will prune later. For recovered AI staging/yoink trees, dedupe by recursive file content hashes, delete/move only inside the approved staging roots, compare against canonical AI state read-only, and leave a manifest. See `references/local-ai-staging-hash-dedupe-cache-cleanup.md`.
  - When consolidating Linux and Windows device-dump agent state, namespace each source under one staging root first. If Semyon asks for Linux-equivalent paths, merge Windows provider roots into the Linux-home namespace recursively: drop same-path SHA-256-identical files, preserve different-content collisions with a source suffix, and never overwrite. Then rerun internal dedupe against the normalized tree.
  - For identical files with different POSIX metadata, do **not** hardlink them if that would change mode/owner/xattrs. On Btrfs, reflink the data into a replacement inode, restore the destination metadata, and then re-hash every staged regular file against the pre-dedupe manifest. This yields shared storage without weakening secret-shaped files or losing provenance paths.
  - Treat T3 state as exceptional. Never bulk-copy or concatenate `.t3/userdata/state.sqlite`, `-wal`, `-shm`, sessions, or event logs into live state. Inspect schemas and merge only on offline copies using primary-key-aware SQLite operations. If Semyon explicitly says to retain only `.t3`, prune the exact sibling provider roots one at a time, verify `.t3` before and after, and remove temporary audit artifacts when he asks for a clean staging area.
  - For a requested staged-to-live merge, first SHA-256 classify every staged file as already-at-destination, already-present-at-another-live-path, missing-path, different-content collision, stateful DB/log, or cache/vendor. Merge only content-addressed artifact stores that pass an application-specific preflight (for example Ollama blobs plus manifests whose referenced blobs exist), copy to an atomic temporary sibling, hash-verify, then publish manifests last. Keep provider identity keys, histories, SQLite/WAL state, logs, Git internals, and vendor trees staged unless separately approved.
- For a user-approved migration of archived AI-provider roots from device dumps, namespace each source below `ai-staging` (for example `device_dumps/linux-laptop/...` and `device_dumps/windows_pc/...`), copy with Btrfs reflinks where available, SHA-256 verify every regular file plus directory/symlink structure, then remove each source root only after its own verification succeeds. Include explicit provider roots (`.claude`, `.codex`, `.t3`, `.t3-code*`, Cursor, Gemini, Copilot, Ollama, and discovered provider config subtrees), but never sweep generic `.config` or live homes. For internal staging dedupe, hardlink byte-identical files only when POSIX metadata matches; for identical content with different mode/owner/xattrs, use Btrfs reflinks so content extents are shared without weakening secret-file metadata. Follow with a full post-dedupe SHA-256 manifest verification. If an SSH-launched destructive NAS task times out, inspect the remote process and target state before retrying: the remote process can outlive the local client timeout, and a second deletion worker can race it. For recovered AI staging/yoink trees, dedupe by recursive file content hashes, delete/move only inside the approved staging roots, compare against canonical AI state read-only, and leave a manifest. See `references/local-ai-staging-hash-dedupe-cache-cleanup.md`. 
- For `/mnt/media` NAS capacity, separate `df` capacity from client-side `du` visibility. Hidden snapshots/datasets/permissions/export loops can make `du` undercount. Recommend direct NAS-side inspection before deleting.
- For selective offsite-backup discovery, do not equate NAS capacity or a broad user directory with the recovery set. Perform direct NAS-local, read-only measurements (logical and allocated bytes, file counts, errors) and break down all large user/laptop/device-dump trees before deciding an allow-list. Serialize deep size scans and exact-duplicate hashing so the NAS is not thrashed. Device dumps, dated snapshots, recycle copies, and staging copies are preservation candidates that require canonical-version and restore-value review; `fdupes` may identify exact duplicates read-only, but never authorize deletion by itself. If Semyon asks not to delegate a deep NAS inventory, keep the audit directly controlled rather than delegating. See `references/nas-selective-offsite-source-inventory.md`.
- For Docker stacks binding `/mnt/media` (especially Servarr), a restored NFS mount does not mean previously failed containers recovered. Check stopped containers for mount errors, restart/recreate with the stack's `--env-file`, then verify app API health and client/indexer tests. See `references/servarr-nfs-mount-recovery.md`.
- For an old Arr Downloads backlog that qBittorrent no longer tracks, inventory via the app APIs before mutation. Container API paths use `/downloads`, not the host's `/mnt/media/arrs/downloads`; Radarr/Sonarr imports are `ManualImport` commands with explicit `copy` mode, while Lidarr needs an exact existing-artist match before an artist-scoped scan. After user-approved cleanup, delete only history-backed source files whose destination size and SHA-256 match, with a JSONL receipt; snapshots can prevent `df` from reflecting logical cleanup immediately. See `references/servarr-manual-import-and-verified-source-prune.md`.
- For a legacy Arr Downloads dump that was not tracked by qBittorrent, use app API manual-import discovery plus `ManualImport` command jobs—not blind moves or an assumed folder watcher. Serialize NFS-heavy imports, map host paths to container paths precisely, preserve sources with copy mode, and only prune source files after paginated Arr-history, size, and SHA-256 verification. See `references/servarr-bulk-manual-import-and-verified-prune.md`.
- For completed releases already sitting in `/mnt/media/arrs/downloads`, preflight each app's manual-import scan and only ingest resolved, unrejected targets. Actual Radarr/Sonarr ingest is a `ManualImport` **command** at `/api/v3/command`, not a POST to `/manualimport`; explicitly set `importMode: "copy"` to preserve qBittorrent sources. Poll one command to completion and verify import history; do not rescan or submit a competing batch while Sonarr is slowly analysing NAS files. For Lidarr, exact-match representative embedded `album_artist`/`artist` tags to existing artists, then require resolved artist/album/release/tracks before a no-overwrite copy import; never bulk-import unmapped audio. See `references/servarr-existing-downloads-backfill.md`.
- Before proposing SSD caching or persistent NFS cache layers, benchmark the full server↔NAS path separately: actual route/interface (do not assume wired LAN), bidirectional `iperf3`, NAS-local direct I/O, NFS direct I/O, then optional SSH transfer. Cleanup bounded test files reliably. Prefer an NVMe working tier for high-churn data over whole-NAS caching; test a temporary `nconnect` mount only after the measurements show an NFS-specific gap. See `references/server-nas-ssd-cache-benchmark.md`.
- For NAS Btrfs snapshots, operate on the NAS host (`semyon@10.0.0.6`) against the real `/mnt/storage` Btrfs filesystem. Create snapshots with existing scripts when appropriate; delete snapshots with `btrfs subvolume delete`, never `rm -rf`; verify with `btrfs subvolume list`.
- Before adding retention inside a NAS backup destination, map its containing Btrfs subvolume and existing snapshot schedule. If the destination is already inside a protected user subvolume (for example `/mnt/storage/users/semyon`), default to **one current rsync mirror** and let the NAS Btrfs daily/weekly/monthly snapshots provide version history. Do not add nested timestamped/hard-linked snapshot retention unless Semyon explicitly requests the extra recovery resolution.
- For large first-time NAS mirrors, write a `COMPLETE` marker only after rsync, host inventory, and manifest generation finish. Treat an absent marker as incomplete regardless of how much data is visible. Enable rsync aggregate progress logging (`--info=progress2,name0`) from the start; large NFS/Btrfs tree scans can make `du` or source-side estimates unreliable during an active copy. Exclude rebuildable dependency trees and inaccessible secret-key directories rather than allowing non-essential permission errors to make the main code/AI-state backup fail; document those exclusions clearly.
- For server-to-NAS protection of code, AI histories, credentials, and recovery state, verify the NFS mount before writing, publish only completed manifested snapshots, then inspect parent-subvolume coverage directly on the NAS. Inner hard-link recovery points plus outer Btrfs snapshots can be sensible layered retention, but neither RAID nor same-pool snapshots is off-site protection. Compare current cron configuration with historical logs before diagnosing duplicate jobs. If an rsync mirror fails, treat its absent `COMPLETE` marker as invalid backup state; identify precise sender errors, exclude only unreadable live runtime files, and retain database-native exports rather than masking errors with `--ignore-errors`. See `references/server-to-nas-backup-btrfs-coverage.md` and `references/server-nas-rsync-mirror-repair.md`.
- **Restic endpoints → NAS:** do not place a restic repository on a client-mounted NFS share, especially one mounted `soft`/with short timeout semantics; an interrupted NFS write can surface as an I/O error at an unsafe moment. Prefer a NAS-local Btrfs repository served to trusted LAN/Tailscale endpoints by `rest-server --append-only` (never public/Tunnel-exposed), with one repository per device and a separate NAS-local maintenance identity for `forget --prune`. Keep endpoint repository passwords in a password manager and local `0600` files—not in the NAS repository, logs, Git, or shell history. Prove NAS Btrfs subvolume/snapshot coverage before calling the design protected; snapshots are local rollback, not off-site recovery. Before committing an include list, inventory `$HOME` one filesystem at a time and classify large `~/.local/share` / `~/.config` children separately: preserve user work, code/Git metadata, notes, chosen media, agent state (`.hermes`, `.t3`, `.claude`, `.codex`) and secret state deliberately; exclude clearly rebuildable caches, trash, package caches, game installs, and NAS media. Treat old recovery bundles and application/editor state as explicit review candidates rather than automatic include/exclude. Do a small PC pilot and disposable restore drill before broadening scope; for laptops, first establish OS, AC/network policy, and actual LAN/Tailscale reachability. Use endpoint timers only for backup; schedule NAS-local checks/retention separately and alert on stale last-good snapshot, failed `restic check`, capacity, and Btrfs health. See `references/restic-endpoints-to-nas.md`.
- For Snapper-managed laptops/workstations, do not apply raw NAS subvolume workflows. Use `snapper --csvout -c <config> list` and `snapper -c <config> delete <num>` while keeping the latest snapshot when requested.
- For media cleanup/dedupe, quarantine first, maintain a manifest, prefer 1080p-ish or higher-quality copies, and delete quarantine only after explicit approval.

## Reporting style
