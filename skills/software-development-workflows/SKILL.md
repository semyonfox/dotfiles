# Software Development Workflows

Use this umbrella when the user asks you to understand, change, debug, test, review, or simplify a codebase. It consolidates the recurring class-level workflows that used to be split across narrow helper skills.

## Choose the workflow

- **Inspect first** when the repository shape, language mix, or ownership boundaries are unclear.
- **Spike** when the right approach is uncertain and a cheap throwaway experiment can de-risk the build.
- **Debug systematically** when there is a failing behavior, error message, performance regression, or flaky test.
- **Use TDD** when adding behavior, fixing a bug with a clear reproduction, or preventing regression.
- **Request/perform code review** before committing or handing off meaningful changes.
- **Simplify code** after a patch works but may be overbuilt, duplicated, or hard to maintain.
- **Attach a language/runtime debugger** when logs and tests are insufficient and live state is needed.
- **Use dynamic multi-agent fanout** for broad or uncertain repo work. Do not impose a fixed low agent count as workflow policy; scale subagents to the task's breadth, risk, and uncertainty, then tune from measured cost/quality/time results.

## Multi-agent fanout policy

For Semyon's Theo-style software work, prefer adaptive fanout over static limits:

- Tiny direct fixes may need **0** subagents.
- Normal bugs/reviews often need **1-3** focused subagents.
- Serious repo diagnosis may need **3-6** parallel specialists.
- Broad audits, migrations, or issue discovery may need **10-30** agents in waves.
- Massive sweeps may justify **50-200** agents, but only with batching and reducer/summarizer passes.

Runtime caps are engineering controls, not workflow philosophy. If concurrency is capped, run agents in waves rather than shrinking the investigation. For large runs, structure as scouts → validators/specialists → reducers → implementers → final reviewer. Keep subagent prompts narrow, restrict toolsets when possible, and summarize findings before feeding them back to the parent context.
- **Fan out to agents dynamically** when repo breadth, uncertainty, or review surface exceeds what one context can inspect well. Do not hard-code a low agent count into the workflow: tiny tasks may need zero agents, normal debugging/review may need 1-3, serious repo diagnosis may need 3-6, and broad audits/migrations may need many agents in waves with reducer summaries.

## Repository inspection

For codebase reconnaissance, use `pygount` or native project tools to count languages, file counts, and generated/vendor directories. Exclude dependency and build directories before drawing conclusions. Preserve the exact command and exclusions in the report so the numbers are reproducible. Full prior notes: `references/codebase-inspection.md`.

Before editing application code, resolve ambiguous nouns from the active task context. If the user says “the webpage” after you generated/opened a local artifact gallery, confirm or infer that they mean the generated gallery page rather than the production website. Do not reflexively patch the app homepage just because a repo is nearby; artifact-delivery pages, browser tabs, docs previews, and production pages are different surfaces.

When the user names a locally installed/open-source app or reference implementation, inspect the installed source/repo before web-searching adjacent products with similar names. For example, “T3Code” in Semyon's environment means the T3 Code app/source checkout, not T3 Chat; search local paths and package/source files first, then use web only if local source is unavailable.

When asked to diagram or report a system that has migrated away from an old infrastructure/provider, reconstruct both sides deliberately: read current docs/config for live truth, find the migration boundary in Git history, inspect old infra files with `git show <commit>:<path>` / `git grep <commit>` rather than switching a dirty repo, and label diagram nodes as current, historical/retired, target/future, external, config, and data. Include provenance and a migration map from retired services to current replacements. Detailed recipe: `references/reconstructing-retired-infrastructure-from-git.md`.

## Version-control setup and jj colocation

When adding Jujutsu (`jj`) to an existing Git repo, use colocated mode and preserve the user's current work. Inspect Git status/remotes first, initialize with `jj git init --colocate`, set repo-local identity from existing Git config, fix `trunk()` to the repo's real integration branch if jj guesses wrong, and verify both `jj status` and `git status`. Do not auto-rebase user changes after setup; report if the working copy is behind trunk and give the explicit `jj rebase -r @ -d <branch>` command. Detailed recipe: `references/jj-colocated-git.md`.

## Spike / experiment workflow

A spike is a disposable experiment, not production work. Define the question, build the smallest proof, run it, and end with a verdict: `VALIDATED`, `PARTIAL`, or `INVALIDATED`. Do not quietly promote spike code into production without a cleanup pass. Full prior notes: `references/spike.md`.

When evaluating a tool concept that may already exist, run both sides of the check: verify the local repo’s implemented behavior with native tests, then do a competitor/adjacent-tool scan and state the differentiated wedge. For Git-hosted executable runner ideas, “npx for GitHub” is already mostly covered; the useful wedge is manifest-driven, permission-aware preflight and execution policy. Detailed notes: `references/git-hosted-runner-concepts.md`.

When building a standalone CLI from an app integration, seed from the proven app code but strip app-specific auth/session/DB/storage concerns, use adjacent MCP/tool manifests as endpoint inventory, add tiny real smoke flags before touching live credentials, and verify upstream API docs before claiming coverage. For Canvas LMS export CLIs specifically, see `references/canvas-export-cli-api-verification.md`.

When Semyon wants a small standalone CLI seeded from an existing TS/JS app implementation and asks for a sendable single executable, prefer a Bun-compiled TypeScript repo when speed and source reuse matter. Strip app coupling, add bounded smoke-test flags before any long real-world run, support token-file/env secret input, verify with unit/typecheck/compile/help plus a tiny real capped smoke test, and inspect the produced archive/artifact. Detailed recipe: `references/typescript-bun-single-binary-cli-handoffs.md`.

When auditing local AI usage/spend dashboards, separate aggregate exports from live provider scans, compare totals by provider/model/date, and audit path normalization independently from cost totals. Running a tool from `$HOME` does not imply it scans archived session corpora under project folders; missing spend often comes from unconfigured provider roots. Treat sluggy project names as lossy, prefer normalized paths, and check Windows/WSL/Linux path equivalence plus worktree rollups before trusting project breakdowns. Detailed checklist: `references/local-ai-usage-dashboard-audits.md`.

For a local dashboard that scans optional agent/project directories, an inaccessible path must be treated as a skipped source, never as a fatal scan error that turns `/sessions`, `/analytics`, and `/projects` into 500s. Reproduce the scan directly, identify the exact optional scanner, wrap only filesystem discovery/read operations in an `OSError` boundary, then restart and verify all three live endpoints return data. When cross-checking with `bunx ccusage --json`, retain both raw JSON artifacts and compare token/cost totals by agent. `ccusage session --json` exposes an agent plus session identifier and usage metadata, but generally no project/CWD; only call a project-cost view a reconciliation if session IDs have been joined to native transcript/session metadata. Report unmatched agents/IDs and pricing-policy differences explicitly rather than summing incompatible rollups. For forecasts/charts, label a month-to-date observation separately from a run-rate projection, state the formula, use soft/hard guardrails as recommendations rather than facts, and visually inspect the exported PNG before handoff.

When Semyon asks whether he has a local project around AI/agent usage, `ccusage`, CodeBurn-style dashboards, or spend analysis, search for both raw usage exports and repo/package roots, then verify the candidate with its native build/test/report commands.

### TypeScript 7 native-compiler migrations

For TypeScript 5.x/6.x → 7 migrations, treat the native compiler and the programmatic compiler API as separate compatibility surfaces. TypeScript 7.0 has a native `tsc` but no stable programmatic API, so framework/lint/tooling consumers can require a TypeScript 6 compatibility alias while project typechecks use TS7 explicitly. Do not trust a bare `tsc` after aliases are installed: assert the TS7 binary/version from the exact package path. Baseline checks, scan removed TS6 options, run framework type generation (for Astro, `astro sync`) before direct `tsc`, then validate framework checks and TS7 checks separately. Make the migration in a clean worktree if the canonical checkout has unrelated user changes, commit it alone, and merge only non-overlapping files. Full recipe: `references/typescript-7-native-compiler-migrations.md`. For alias/bin resolution, pnpm workspace paths, and TS7 config removals verified in real migrations, see `references/typescript-7-workspace-aliases.md`. For the decision table, nested-package handling, clean-worktree merge guard, and validation evidence from several real migrations, see `references/typescript-7-practical-migrations.md`. When asked to quantify improvement, benchmark exact explicit compiler binaries on the same checkout with three warm samples and report medians; see `references/typescript-7-benchmark-and-visual-reporting.md` for the reproducible protocol and a visually QA'd Discord-slide format.

When running ecosystem/dependency hygiene tools such as `@e18e/cli` across many projects, default to **analyze-only sweeps** with raw JSON + a filtered Markdown report. Discover only relevant JS/TS repos with lockfiles, exclude archives/worktrees/reference dumps, and never run broad `migrate --all`/codemods without explicit per-project approval. Treat findings as triage: direct replacements like `uuid` may be good candidates, auth/client libraries like `jsonwebtoken` or `axios` need semantic review, and vendored/generated-file suggestions are usually noise. Detailed workflow: `references/e18e-dependency-hygiene-sweeps.md`.

When Semyon wants to try e18e across projects, treat it as a read-only JS/TS dependency audit first: run pinned `@e18e/cli` `analyze --json --report-level warn` only on repos with `package.json` plus a supported lockfile, capture per-repo JSON and a short rollup, and do not run `migrate --all` globally. Any migration should be narrow, dry-run first, diff-reviewed, and test-verified in a clean git branch/worktree. Detailed workflow: `references/e18e-js-ts-dependency-audits.md`.

## Systematic debugging workflow

Follow root-cause order:

1. Read the exact error and reproduce it.
2. Inspect recent changes and relevant invariants.
3. Add instrumentation or use a debugger to observe live state.
4. Fix the smallest root cause.
5. Verify with the narrow failing case and then the broader suite.

For live services, confirm process, port, logs, config, and data dependencies before editing. When a requested dashboard port returns a plausible-but-wrong page or 404, prove listener ownership before restarting anything: compare the intended process command/environment with `ss`/`lsof`, probe both the intended and actually running frontend ports, and inspect Docker published-port mappings. A port occupied by an unrelated container is not a reason to kill it; keep its service intact and report the working dashboard URL or ask before a port migration. If a telemetry/session scan fails because one optional source is unreadable, catch `OSError`/permission errors at the per-source boundary and continue scanning other sources—an inaccessible project-owned trace path must not turn aggregate `/sessions`, `/analytics`, or `/projects` endpoints into 500s. Verify the repair against the live API endpoints, not only a frontend shell or compile check. For Docker Compose E2E stacks, distinguish service reachability from Docker healthcheck/exec health: a service can answer host `curl` while healthchecks fail because the container was created from a deleted/stale bind-mounted worktree; inspect `.State.Health` and mounts, then recreate only the affected service.

For Jenkins-on-push failures, first establish the **authoritative pipeline definition**. A job may be seeded from a separate infrastructure repository and its stored job config can differ from the app repo's `Jenkinsfile`; compare the build log, job `config.xml`, and seed Job DSL before patching. After updating the source, reload/reseed Jenkins, confirm the stored job script contains the fix, trigger the normal path, wait for the final job result, and probe the deployed service. From a Jenkins container, do not assume its Docker bridge gateway reaches a host-bound database; verify the candidate database endpoint from the Jenkins network namespace first. If a minimal Node/Debian builder fails to initialise HTTPS because no CA certificates are available, install `ca-certificates` in the builder stage and rerun the exact image build. Detailed procedure: `references/jenkins-managed-pipeline-source-triage.md`.

Full notes: `references/systematic-debugging.md`, `references/postgres-vs-mariadb-performance-triage.md`, and `references/docker-compose-e2e-stale-bind-mount-healthchecks.md`.

### Embedded desktop-game lifecycle bugs

For a Java Swing/desktop game embedded in a browser runtime, debug the *game thread* as well as the browser frame. If an initial keypress causes a jump to a later wave, frozen render, or `NullPointerException` in collision code, inspect startup publication order: do not mark gameplay active until the player, enemy array, UI state, and projectile collection have all been initialized. Use a volatile active-state flag (or equivalent synchronization) and publish it last; retain null guards at collision boundaries. Treat restart as an explicit state reset, including score/currency, wave/frame counters, health, input flags, bullets, bosses, and every upgrade-derived stat. Do not let display-only upgrade levels reset while their hidden effects persist.

For descending enemies, make crossing the player/invasion line an explicit loss condition before sprites can travel below the viewport. Separately test direct collision and invasion-line loss. Balance upgrades against the actual income curve, not isolated prices: make one or two early choices affordable after the first wave, keep major upgrades reachable rather than arbitrary, use predictable scaling, and ensure a max-health purchase also grants usable health when that is the intended player-facing result. Preserve UI unchanged when the requested scope is mechanics-only.

When publishing a rebuilt JAR/static game through a Git-triggered Jenkins/Docker deployment, verify source and artifact commits independently, compile the JAR, run the host site's checks/build, then inspect the Jenkins build log and the JAR hash inside the newly recreated serving container. A public CDN may still serve a stale asset due to cache TTL even after origin deployment succeeds; report origin-versus-edge state separately and purge the exact asset when authorized/credentials permit. Full reproduction and verification notes: `references/embedded-java-game-lifecycle-and-cdn-deploy.md`.

For a Java Swing game embedded in a browser runtime such as CheerpJ, test the deployed artifact rather than trusting that the iframe loaded: click/focus the iframe, trigger the start control, wait beyond transient banners, inspect the browser console for Java-thread stack traces, and capture the frozen/rendered state. If an NPE appears in collision or game-loop code immediately after start, inspect startup ordering across threads. A common bug is publishing `isGameInProgress = true` before all world objects (especially the player and initial entity array) are initialized; the loop can then both call collision detection with a null player and advance a wave by treating an incompletely populated array as all defeated. Construct/reset the complete world first, then make it active; retain defensive null guards around collision operands. Report the live reproduction, console trace, visible consequence, and source-level race separately from optional UI issues such as controls focus instructions or unreadably small in-game panels.

Full notes: `references/systematic-debugging.md`, `references/postgres-vs-mariadb-performance-triage.md`, and `references/docker-compose-e2e-stale-bind-mount-healthchecks.md`.

For stateful desktop/remote tools with a client app, headless server, SSH tunnel/proxy, saved credentials, and a local state DB, split the investigation into package identity, process/port ownership, state-directory aliases, tunnel lifecycle, and clean-state isolation. Correlate server connect/disconnect traces with client tunnel logs and OS auth logs before blaming versions or generic network flakiness. If the intended outcome is an automatic headless backend, build a single-instance user systemd service with a preflight guard and verify exactly one listener/DB holder. If pairing works in browser but fails in the desktop app, compare the exact environment URL and check for dropped ports/scheme before changing the server. When state-dir aliases such as `~/.t3`/`~/.t3-code` are involved, prefer a no-alias canonical real directory. If the canonical main dir is upstream-default `~/.t3`, remove explicit service/script `T3CODE_HOME`/`--base-dir` overrides unless there is a specific reason to keep them; if using any non-default dir, make the override explicit. Verify process args and HTTP readiness. For SQLite-backed state, compare live snapshots against a disposable clean schema before touching tables; expired unused pairing links can be cleaned surgically only when authorized, while duplicate-looking threads should be analyzed separately from destructive cleanup. For T3 Code recovery/consolidation work, do not treat `state.sqlite` as disposable cache: build a timestamped staging tree, hash-dedup files, group/merge SQLite DBs by schema, run migrations only on copied DBs, skip old auth/pairing by default, and import projection history only through a cloned-live dry run. Be especially careful with old T3 schema groups: older 16-table DBs may migrate cleanly to current, while 40+ table `WorkflowSchema` DBs may be future/branch artifacts rather than simple old versions. For the final canonical live merge, take T3 offline, make a verified SQLite backup, dry-run into a cloned live DB, dedupe event logs by both `event_id` and `(aggregate_kind, stream_id, stream_version)`, remap imported event sequences, relink command receipts by `command_id`, and advance `projection_state` only after imported projection rows are already present. When communicating findings, give the user a short human overview plus attachable full reports/diagrams rather than iterating walls of “AI forensic” text in chat. Detailed checklist and report-writing guidance: `references/stateful-remote-desktop-debugging.md`; T3 Code state/auth/duplicate triage notes: `references/t3-code-state-path-auth-sqlite.md`; T3 SQLite recovery/staging/migration workflow: `references/t3-sqlite-recovery-staging-migrations.md`; final canonical merge notes: `references/t3-sqlite-canonical-merge-recovery.md`; starter service template: `templates/single-instance-headless-systemd.service`.

For Electron/AppImage desktop apps on Arch-style systems that fail from CLI/launcher with `Exec format error` or “problem with the binary,” verify the payload before reinstalling blindly: inspect wrappers and desktop entries, run `file`/`readelf`/`xxd` on the target binary, use `pacman -Qo` plus `pacman -Qkk` to distinguish package metadata from corrupted installed files, and if sudo is unavailable, repair user-locally by extracting the verified AppImage from the AUR cache into `~/.local/opt`, rewriting `~/.local/bin` wrappers, and updating the user desktop entry. Verify via the real graphical session environment and an app/backend health endpoint rather than trusting `--version`, since Electron apps may hang or launch the GUI for version/help flags. Detailed recipe: `references/electron-appimage-cli-launch-repair.md`.

## Dockerfile and container-image optimization

When Semyon asks to inspect or improve Dockerfiles across active projects, distinguish canonical repositories from backup/worktree/reference copies, inspect the *actual* Compose/Jenkins build context for each image, and preserve unrelated dirty work. Default Node/Python application builders and runtimes to Debian `*-slim` / Bookworm rather than Alpine unless the project’s dependency chain has been built and exercised successfully on Alpine. For a pure static frontend, Alpine nginx can remain a deliberately tested exception; report the measured image-size/runtime trade-off rather than treating image size as the only metric.

Apply improvements in this order: context hygiene and secret exclusions; manifest/lockfile-before-source cache ordering; multi-stage runtime reduction where it removes real build tooling; deterministic package-manager invocation (`npm exec`/`pnpm exec` rather than registry-falling `npx`); BuildKit cache mounts with a deliberately configured package-store path; then runtime hardening/deployment changes. A child `.dockerignore` only applies when that directory is the actual build context; root-context `docker build -f client/Dockerfile .` requires root ignore rules. Context-local allow-list ignores are especially useful for Rust API subcontexts. Do not bake passwords or complete connection URLs into `ENV`; require them at runtime.

For production base images, retain a readable version tag and pin the multi-architecture manifest digest (`image:tag@sha256:…`). Resolve it with `docker buildx imagetools inspect <image>` and take the top-level `Digest:` field; validate the resulting Dockerfile build. Pair digest pins with GitHub Dependabot `package-ecosystem: docker` schedules in every directory containing a Dockerfile. Docker Scout's retired GitHub integration is not the update path.

When Semyon asks which image/base is “best”, do not answer from generic Alpine-vs-slim advice. Treat it as a bounded bakeoff using the project’s real context, lockfile and runtime smoke path. Compare a small matrix: current validated baseline, newest plausible compatible runtime, and (for static apps) slim builder + Alpine nginx versus slim/Bookworm nginx. Measure final image bytes, no-cache build duration, and actual published-port HTTP readiness; label cold-build timings as approximate because registry/network state can affect them. Choose the Pareto winner: latest compatible supported runtime for builders/servers, with the smallest tested runtime image. In static multi-stage images, the nginx runtime determines final size, while the Node builder normally does not—so Debian slim builder + a tested pinned Alpine nginx runtime is often the best hybrid. Use Alpine for a static runtime only after that project’s real build and smoke test pass. For temporary parameterized Dockerfile bakeoffs, declare every build-arg used in a `FROM` before the first `FROM`; stage-local `ARG` declarations cannot supply a later base-image reference.

### Base-image bakeoffs and version upgrades

When Semyon asks which base is “fastest/smallest/most efficient”, do not answer with a universal Alpine-versus-slim rule. Make a small real-project bakeoff using temporary Dockerfiles and the exact production context, then select the smallest **validated** option. For static frontend images, benchmark the builder and runtime independently: the nginx runtime dominates final image size, while the Node builder disappears in a multi-stage image. A strong default after validation is a current Debian-slim Node builder plus a pinned Alpine nginx runtime; this preserves glibc/native dependency compatibility during builds while retaining the small static runtime. Keep a Bookworm nginx runtime only when a runtime-specific dependency, module, or integration actually requires it.

Treat major-runtime upgrades separately from base-family selection. Test the newest supported runtime against the full real build and final runtime contract before adopting it; `engines`/lockfile compatibility and a successful build are necessary but not sufficient. For a Node service or MCP, align builder and final Node major (including distroless) where practical. Prefer a current supported release that passes over an older release that wins a noisy few-second cold-build timing race. Record build time, final image bytes, and a real smoke command; label no-cache timings as approximate because registry/download conditions affect them. Do not apply a broad major upgrade to Rust/Python services merely because the tag exists—upgrade only after their project dependency build succeeds.

Verification must build each changed image from its real context, not just parse the Dockerfile. For static nginx images, start it with `docker run -d -p 127.0.0.1::80 …`, read the assigned port with `docker port`, and curl the actual rendered root. Do not omit `-p`: an un-published port makes `docker port` empty and can accidentally curl unrelated host port 80. For workers, invoke the production command/binary with `--entrypoint` to prove local runtime resolution; for Compose edits, use `docker compose --project-directory <repo> config --quiet`. Finish with `git diff --check`, report preserved pre-existing changes separately, and remove only verification tags/logs created during the audit.

## Test-driven development

When behavior can be specified, use RED-GREEN-REFACTOR:

1. Write or update a focused test that fails for the right reason.
2. Run the specific test and capture the failure.
3. Implement the smallest change.
4. Run the specific test, then the relevant broader suite.
5. Refactor only with tests green.

## Pre-commit review and quality gates

Before declaring code ready, inspect the diff, scan for secrets/injection/deserialization/SQL hazards, run formatters/linters/tests appropriate to the project, and re-open the diff after auto-fixes. Full prior notes: `references/requesting-code-review.md`.

For agent-driven PR review or issue discovery, do not stop at the changed lines. Read the diff, identify the affected module/API/component, then trace callers/callees and related tests/config/docs one or two layers deeper. A useful review comment or issue should explain the concrete connection between the diff and the wider behaviour it may break. Avoid generic style nits and vague “improve architecture” issues unless they are tied to a specific failure mode or maintainability risk.

For dependency hygiene sweeps using tools like `@e18e/cli`, run analyze-only first, classify duplicate-transitive findings separately from direct replacement candidates, and avoid global codemods. Keep raw JSON plus a filtered active-repo report, then make only small verified changes such as unused dependency removal, lockfile-only dedupe, or safe `uuid` v4 → `crypto.randomUUID()` replacement. Auth/security libraries such as `jsonwebtoken`, HTTP clients with cookie/redirect semantics, and old framework-stack duplicate deps are design decisions, not quick fixes. Detailed workflow: `references/e18e-dependency-audit.md`.

When a stale PR shows merge conflicts, first check whether the conflict is real feature disagreement or just drift from work already merged differently. Use `git merge-tree`, `git range-diff`, and a throwaway worktree to salvage only the remaining useful delta onto the current base. Prefer a fresh small replacement PR over manually resolving a broad stale branch. Detailed recipe: `references/stale-pr-salvage.md`.

For Semyon-facing multi-item triage, avoid dumping a long queue of approvals. Present one concrete recommendation at a time, ask for approve/deny, execute and verify if approved, then move to the next item.

When using subagents for software work, choose fanout from the task, not from a fixed template. Use parallel batches for independent areas, wave-based execution for very large sweeps, and reducer agents/summaries before sending many findings back to the parent. Runtime concurrency caps are engineering controls; they should shape batching, not become artificial workflow ceilings.

## Simplification / cleanup workflow

When the code works but may be too complex, review it from three angles: correctness regressions, maintainability/readability, and deletion/consolidation opportunities. Apply only changes you can verify. Full prior notes: `references/simplify-code.md`.

### Removing a user-local service or developer tool

For an explicit request to remove a locally installed service/tool, treat it as a lifecycle cleanup rather than only deleting the visible executable:

1. Inventory the exact unit/process, executable ownership/path, config/state/credential roots, listener port, autostart entries, containers, and wrapper/caller references before mutating.
2. For a user systemd service, stop and disable it first, remove its unit and `default.target.wants` symlink, then run `systemctl --user daemon-reload`. Do not stop unrelated services merely because they use a nearby port or name.
3. Remove the requested binary plus its dedicated config, state, backups, and credentials only after the inventory confirms their ownership. Do not read or expose credential contents merely to identify a directory.
4. Preserve useful adjacent wrappers where possible, but remove the retired tool's special flags, authentication/config paths, and model/provider routing. A wrapper that now uses a native provider should explicitly unset stale proxy/provider environment variables so inherited shell state cannot resurrect the removed integration.
5. Validate the wrapper with its syntax checker and a harmless help/smoke invocation. For environment scrubbing, put a temporary harmless stub executable first in `PATH`, invoke the wrapper with old proxy variables set, and assert the stub receives none of them.
6. Verify removal through all relevant layers: systemd says `not-found`/inactive, no matching process, no listener on the old port, dedicated paths are absent, and scoped config/bin/state searches find no active references. Report removals and verification concisely.

Do not claim full removal based solely on a deleted unit file; a running process, enabled symlink, caller wrapper, or inherited proxy variable can leave the integration operational.

### Claude Code through a local multi-provider proxy

When configuring Claude Code as the client/UI for OpenAI-, Gemini-, or other compatible upstream models, keep the proxy route **explicit and local** rather than globally redirecting Claude:

1. Keep native `claude` unproxied. Provide a separate wrapper (for example `claudex`) that alone sets `ANTHROPIC_BASE_URL` and its local proxy token; explicitly unset stale proxy variables in the native path.
2. Bind the proxy to `127.0.0.1`, use a dedicated local client key with restrictive file permissions, disable remote management/control panels unless truly needed, and verify the listener/process/unit.
3. Require an explicit `--model` for proxied runs. Never map all Claude tiers (Opus/Sonnet/Haiku/subagents) to one premium upstream model: it hides billing/quality choices and turns supposedly cheap helpers into premium calls.
4. Treat reasoning as a **per-request upstream setting**, not a wrapper default or a per-model hardcode. For CLIProxyAPI, transform `claudex --model MODEL --effort LEVEL` into `MODEL(LEVEL)` and let the proxy translate it to the provider-native request field. With no effort specified, preserve the provider default.
5. Do not force Claude Code's own normal effort control for a proxied run alongside an upstream model-effort suffix; they are distinct controls and can create confusing double-control behaviour. Reject an effort value with no documented proxy equivalent rather than silently mapping it to a more expensive value.
6. Treat **Claude Code `ultracode` as the explicit exception**: it is client-side dynamic-workflow orchestration, not an upstream reasoning level. Pass it through to Claude Code unsuffixed (`claude --model MODEL --effort ultracode`), never translate it to provider `ultra`/`max`, and do not claim it works upstream until a bounded authenticated request is observed. Keep it off for routine edits because workflow fan-out can substantially raise usage.
7. Before considering the route usable, perform a tiny authenticated smoke request and inspect the proxy's sanitised log/effective payload to prove that the requested model and reasoning level reach the actual upstream provider. ## Frontend calendar and timezone changes

When reviewing calendar, scheduling, date-range, or local-day grouping changes, verify the time model before approving. The safe pattern is: store/query UTC instants, render by local calendar date, and convert local wall-clock visible boundaries to ISO instants before API/database range queries. Do not append `T00:00:00Z` / `T23:59:59Z` to a local date key unless the UI is explicitly UTC-based; that can miss or misplace records around midnight and DST. ## Compliance-sensitive integrations

When moving hardcoded API keys, provider config, credential paths, or local absolute paths out of repo utility scripts, treat it as a small security/config migration: validate without printing secrets, move secrets to ignored `.env`/platform secrets, keep safe defaults in `.env.example`, harden `.gitignore`, add runnable checks, and report committed-history rotation risk. Detailed notes: `references/env-secret-migration.md`.

When running dependency hygiene tools such as `@e18e/cli`, start with analyze-only reports and split findings by risk before mutating. Treat duplicate transitive deps, unused deps, direct replacement candidates, and native syntax suggestions differently. Lockfile-only dedupe is usually the safest class; auth/JWT libraries, HTTP clients with cookie/redirect semantics, CLI parsers, UUID strategy, Cloudflare/toolchain skew, old CRA/Jest stacks, and workspace drift are design decisions unless explicitly scoped. Do not remove or replace a dependency merely because a scanner flags it if the repo is old/stale or the dependency participates in auth, IDs, build/deploy, cookies, redirects, or CLI behavior. After any agent/subagent claims a dependency change, inspect the real diff and searches yourself, and if Semyon calls a cleanup dangerous or asks to revert, revert immediately and verify the relevant diff is empty. Detailed workflow: `references/e18e-dependency-audit.md`.

When reviewing auth, account deletion, vault deletion, rate limiting, or abuse controls, separate public UX from internal observability. For rate-limit store failures on sensitive flows, fail closed with a generic public `503` + `Retry-After`, while logging the exact store/category/error internally and emitting metrics. ## Compliance-sensitive integrations

When reviewing LMS/edtech integrations, treat platform policy and institution approval as separate blockers from GDPR/legal compliance. Canvas-style manual API-token flows may be fine for private testing but not for public multi-user launch; prefer OAuth Developer Keys or institution-approved LTI, scoped read-only where possible. Start by tracing the actual app: Canvas may import course data while ordinary credentials/Google/GitHub auth already handles account identity, so do not prescribe university SSO without proving it solves a real need. A Canvas Developer Key does not bypass a university: tenant keys are controlled by the institution’s root Canvas admin, while Instructure-created global keys still need each tenant enabled. A rejection of Entra/OIDC identity permission is not technically a Canvas-data decision, though it is a governance signal. For AI over LMS data, trace the data into storage, embeddings, logs, prompts, and deletion paths, and use read-only allowlists for AI tools rather than subtractive disabled lists. For Canvas/document import deduplication, do not equate equal SHA-256 bytes with cross-tenant entitlement: start with per-user caching, then allow reuse across a documented authorization domain only for explicitly eligible official course material—not submissions, feedback, private uploads, or ambiguous attachments. Model physical immutable blobs, versioned extraction/embedding derivatives, and user-visible document references separately; keep annotations user/reference-scoped. Every serving/export/presigned route must authorize a live logical reference before resolving a shared key. Ordinary note cleanup must delete only that user's projection; shared blobs/derivatives require reference-aware retention and a separate race-safe GC. Do not use pooled session advisory locks to serialize long OCR/network work; use a durable claim/lease state machine, publish a cache as replayable only after chunk/vector completeness, and version/refresh it after final enrichment. Detailed notes: `references/lms-integration-compliance.md`, `references/content-addressed-lms-import-deduplication.md`.

## Privacy-conscious early product analytics

When Semyon asks whether a product is ready to collect early funnel data without an intrusive cookie banner, inspect both repository intent and live browser behavior. Do not infer deployment from docs alone.

1. Inspect code and canonical docs for first-party events, third-party vendors, storage, retention, and feature gates.
2. Probe the live public page for `Set-Cookie`, `document.cookie`, local/session storage keys, loaded scripts, and actual network resources. A vendor string in a bundled chunk does not prove the vendor is active.
3. Separate strictly necessary auth/security cookies such as refresh or CSRF tokens from analytics identifiers.
4. Prefer a small first-party event endpoint for public acquisition events: no browser persistence, no raw IP retention, short-lived or rotating anonymous aggregation, and respect for DNT/GPC.
5. Record authenticated activation milestones server-side where possible instead of adding more browser tracking.
6. Treat `sessionStorage` and `localStorage` identifiers as browser storage requiring their own consent/privacy review. “No analytics cookie” is not enough if an analytics identifier is written elsewhere.
7. Cookieless Plausible-style page measurement may fit a no-banner posture, but keep PostHog persistence, autocapture, identification, advertising pixels, heatmaps, and session replay disabled until consent, access, and retention are explicitly decided.
8. Report code state and live state separately, and label the conclusion as technical/privacy guidance rather than formal legal advice.

The goal before launch is not a grand dashboard. Track source, first useful action, activation, return, and drop-off with the least invasive mechanism that answers the question.
